# 任务栏提示：可行性预研究

日期：2026-10-23。分支：`research/taskbar-toast`。基线：`80b5c69`（main）。

本记录依据现有代码与微软文档，尚未制作或运行任务栏原型。以下尺寸、降级规则和实施阶段是讨论提案，不代表已验证的效果。当前分支只新增本文，程序、设置、版本号和主线均未修改。

## 需求理解

提供可选的提示位置：复制反馈短暂出现在任务栏左侧的空白区域，视觉上像任务栏的一部分，不新增任务栏应用按钮，不挤动现有按钮，仍不抢焦点。原卡片模式继续保留。

这里的“不占任务栏图标位置”指提示本身；现有通知区域托盘图标仍用于设置和退出。

## 初步判断

**值得做独立覆盖窗口的原型；不建议把 CCCC 窗口挂到 Explorer 内部。**

Windows 11 的公开说明明确列出应用不能再自定义任务栏区域。问题在扩展接口和宿主契约，不能简单归结为权限不足。提升为管理员并不能获得受支持的自定义任务栏槽位。[微软 Windows 11 说明](https://www.microsoft.com/en-us/windows/windows-11-specifications)

| 路线 | 能实现的效果 | 与本项目的关系 |
|---|---|---|
| 独立无边框覆盖窗口 | 外观贴在任务栏表面，不创建程序按钮；任务栏不会自动为它让位 | 建议试验；主要问题是空白区判断、层级和状态变化 |
| 任务栏上方的紧凑提示 | 接近任务栏，通常更容易避免覆盖其按钮 | 可作为空间不足时的另一候选；首版建议直接回原卡片位置 |
| AppBar 桌面工具栏 | 在屏幕边缘分配自己的区域，影响桌面工作区 | 不能等同于嵌入现有任务栏，不符合本需求 |
| Explorer 内嵌窗口 / Shell 修改 | 可能实现更强的“在任务栏内部”效果 | 增加对 Shell 结构、生命周期和 DPI 的依赖，本轮不建议 |

AppBar 文档描述的是独立的屏幕边缘窗口及其预留工作区，并非把控件插入 Windows 11 任务栏。[Application Desktop Toolbars](https://learn.microsoft.com/en-us/windows/win32/shell/application-desktop-toolbars)

`SetParent` API 本身存在，但这不构成任务栏扩展协议。微软明确说明不同 DPI awareness 模式的窗口建立父子关系可能出错，跨进程情况下可能强制重置子进程的 DPI awareness。它也不会自动替应用处理 Explorer 重启、布局分配等问题。[SetParent](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent)

## 已核对的代码

- `src/CCCC/Toast.cs`：WPF 窗口已设置 `ShowInTaskbar=false`、不激活、置顶和非交互。当前按复制来源前台窗口选择显示器，定位到该屏幕工作区左下方；尚未查询任务栏内部空白。
- `src/CCCC/Rendering.cs`：外层绘制范围为 424×144 DIP，四周各 32 DIP 留边，卡片主体约 360×80 DIP。不能仅把现有窗口的 Y 坐标向下移动就当作任务栏布局。
- `src/CCCC/Acrylic.cs` / `CompositionWindow.cs`：背景材质拥有独立的原生 HWND，文字窗口属于它；裁剪区域含固定的 32 DIP 留边。两层定位、显隐、裁剪和层级必须保持同步。
- `src/CCCC/Motion.cs`：淡入 200 ms、淡出 220 ms；重复复制的卡片峰值 1.06、计数总峰值 1.18。任务栏安全范围需要容纳动画峰值及可见阴影，不能只用静止的布局框判断。

直接复用原卡片并整体缩小，会连同文字一起缩小；不符合已有小字清晰度目标。建议单独布局，共用复制判断、提示文案、字体采样和动画状态。

## 推荐试点的外观

- 单行胶囊，初始讨论范围约 200–240×28–32 DIP，最终取决于任务栏实际高度和可用宽度；不是固定的任务栏系统尺寸。
- 保留状态图标、主提示和计数。第二行内容预览先不放进这一布局，原卡片模式仍可提供完整预览。
- 延续现有深浅配色和四倍文字采样；减弱或取消外投影，让其更像任务栏表面的轻量反馈。
- 首次复制仍淡入，重复复制保留短促放大，按显示空间约束峰值；若现有峰值不能完整容纳，应回退而不是裁掉字形。
- 允许用户选择任务栏模式，但默认位置和具体回退策略待讨论后确定。

## 稳定性边界

| 情况 | 建议行为 / 待验证事项 |
|---|---|
| 主屏、底部任务栏常显、左侧确有空白 | 首阶段的目标场景，确认位置、受光、动画与文字效果 |
| 左侧开始菜单、搜索、天气或应用按钮占位 | 不盖住可见交互元素；不能确认安全空白时回原卡片 |
| 应用增多、任务栏布局改变 | 重新计算，过期结果不得继续显示；不能认为左下角永久空闲 |
| 任务栏自动隐藏 | 首阶段直接回原卡片；“是否配置自动隐藏”与“此刻是否展开”需要分别判断，不主动唤出任务栏 |
| 多屏、不同缩放、切换主屏、热插拔 | 首阶段只覆盖已确认的主屏场景；其他屏幕回原卡片，后续再扩展 |
| Explorer 重启 / 任务栏重建 | 丢弃旧句柄和位置结果，重新探测；未恢复时走原卡片 |
| 开始菜单、任务视图、任务栏菜单、全屏应用 | 确认显示优先级；不靠每帧强制置顶抢占 Shell 层级；按场景隐藏或回退 |
| 安全桌面 / 锁屏 | 不尝试越过桌面或权限边界；桌面恢复后再探测 |
| Acrylic 开关与系统材质回退 | 先证明纯色覆盖成立，再验证材质窗口与文字窗口始终同步 |

**“点击穿透”与“不遮挡”是两个验收项。**即使点击能到达任务栏，盖住按钮的文字和图标仍是不合适的视觉行为。

还需单独验证原生材质 HWND 的命中测试，不能只依据 WPF 的 `IsHitTestVisible=false`。`HTTRANSPARENT` 的文档限定其转交语义涉及同线程窗口；不能据此直接证明两个进程之间的穿透已经正确。[WM_NCHITTEST](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-nchittest)

## 定位与空白区探测

- `ABM_GETTASKBARPOS` 提供系统任务栏的屏幕边界，不提供“这里能放一个胶囊”的可用槽位。[文档](https://learn.microsoft.com/en-us/windows/win32/shell/abm-gettaskbarpos)
- `ABM_GETAUTOHIDEBAREX` 能按显示器和边查询自动隐藏 AppBar 的句柄；它不是当前空白区或展开动画进度接口。[文档](https://learn.microsoft.com/en-us/windows/win32/shell/abm-getautohidebarex)
- `TaskbarCreated` 是已有的重建通知机制，适合令探测结果失效；不是空位布局通知。[The Taskbar](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar)
- 为检验现象，可以先在用户明确留空的任务栏区域做固定位置原型；这一阶段不能声称支持自动避让。
- 若继续研究自动避让，可探索 UI Automation 获取任务栏控件边界，再留安全边距。Shell 控件树、第三方任务栏和缺失结果均需保守处理；不能把枚举成功当成完整覆盖的保证。
- 此类跨进程查询不能放在复制反馈的 UI / 逐帧动画路径里。采用有期限的结果快照、去重和活动序号；查询未完成或过期时直接回退，不等待或排队。
- 不把 `Shell_TrayWnd` / `Shell_SecondaryTrayWnd` 等窗口类名和内部子窗口结构当成稳定的公共布局契约。

## 研究顺序与判断标准

1. **视觉与基本行为原型**：仅主屏常显底部任务栏、用户明确留空区域，先用普通背景；证明紧凑布局、首次淡入、连续复制和两层窗口操作不会裁切或抢焦点。此阶段暂不做自动空位识别，不进入主线。
2. **材料与交互原型**：验证 Acrylic 开关、主题变化、动画同步，以及任务栏左键、右键和拖拽不被覆盖 HWND 阻挡。比较第一次出现与连续出现的手感。
3. **有限边界试验**：任务栏拥挤、自动隐藏、Explorer 重建、两种 DPI 与外接屏；验证失败能可靠回到原卡片，且不会留下孤立背景窗口。
4. **决定是否产品化**：只有空位识别和回退规则足够可解释、没有持续轮询或显著额外依赖时，再讨论作为可选项合并。否则保留实验分支。

目前没有运行程序、调整系统任务栏、修改真实配置或开展性能/内存测试。不能从此预研究得出“完全不影响稳定性”或固定的资源开销数字。
